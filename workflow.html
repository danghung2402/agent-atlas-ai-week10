LOOP / GRAPH

大流程分關，
錯誤在附近修正。

這是本作業由 AI 依規格推進的工作流程；固定程式執行檢查，沒有宣稱全自動模型編排。

NODE 01

確認需求

輸入：主題、讀者、來源與主題的直接關係、停止條件

產出：requirements.md

檢查：先確認，再下載或改寫；每份來源要說明與主題的關係

未確認 → 先討論
NODE 02

來源與證據卡

輸入：一次一篇：PDF、證據卡

產出：sources-gate-*.json

檢查：68 項來源與定位檢查；寫完證據卡立即執行，不依賴 HTML

未通過 → 重讀原文／修證據
NODE 03

整理排程 Wiki

輸入：已核對證據卡

產出：13 篇 Wiki

檢查：來源、概念、問答及反向連結

缺概念 → 補該頁
NODE 04

Wiki 查詢與覆蓋

輸入：Wiki＋四個問題

產出：query-gate.json

檢查：五份來源均有對應證據

不足 → 回查詢
NODE 05

逐頁稿

輸入：已選 Wiki 與證據

產出：deck.json

檢查：15 頁；腳本先驗證查詢關卡與輸入雜湊才寫入

說法錯 → 只修該頁
NODE 06

新上下文複核

輸入：逐頁稿與原始 PDF

產出：review.json

檢查：逐項語意、版本與限制；渲染前完成

證據錯 → 回 02；逐頁稿錯 → 回 05
NODE 07

渲染 HTML

輸入：已複核逐頁稿

產出：教學 HTML

檢查：不改研究文字；檢查顯示與操作

版面錯 → 本關修正
NODE 08

最後驗收

輸入：HTML、來源與案例結果

產出：final-checks.json

檢查：連結、內容、案例、版本；UI 另記錄

未通過 → 對應節點；三輪仍失敗則停

哪些地方會重複？

證據卡核對、逐頁稿核對與渲染驗收各有局部 Loop。證據錯只重讀該來源；引用錯只修該頁；顯示錯只修 HTML／CSS，不改研究主張。每關最多三輪；資料不足或原文無法核驗就停止回報。

為什麼這樣設計？

證據錯誤會傳到 Wiki 與簡報，所以本輪在改寫前已先執行 NODE 02。查詢覆蓋也在逐頁稿之前完成；最後仍保留整份語意複核，避免只靠定位詞當成內容正確。
